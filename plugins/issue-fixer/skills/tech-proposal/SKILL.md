# 技术方案报告 · 撰写与拉评审

把一个目标仓库的改动/需求，产出成一份**换个人照着就能零成本上手、评审挑不出硬伤**的技术方案文档。

方法论的固化参考在 `references/`：**金字塔原理**（结论先行 / 归类分组 MECE / 突出重点，见
`pyramid.md`）与**用图表说话**（message-first 选图，见 `diagram-cookbook.md`）。

**核心信念**：一份拉评审就绪的方案要同时做到——
- **零成本上手**：换个人照文档就能干，一切模糊描述换成数字，每个选型/取舍都有明确结论 + 为什么。
- **结论先行、突出重点**（金字塔）：评委 30 秒抓住结论、5 分钟看懂全局、任何一节单拎出来都读得懂。
- **能画图就别堆字**（用图表说话）：达阈值必画，一图一结论。

做不到这三点，方案就是没写完。

## 驱动闭环（六步，不要跳步）

### 0 · 取材与定位

先搞清楚"要给什么改动写方案"，再动笔。缺任何一项就先补齐：

- **需求来源**：若给了 PRD/需求文档链接 → 用已配置的读取通道读全文（飞书链接走
  `scripts/evidence.mjs` 的 docx/wiki 取回），抽出目标/范围/需求点/验收。没有 PRD 就把
  用户口述的需求复述确认。
- **分层定位**：识别改动**触及哪些包/层**——先扫目标仓库的目录结构、workspace 划分、
  既有设计文档目录，得出该仓自己的分层词汇（前端应用 / SDK / 服务端 / 执行器 / 协议包…）。
  是否动 **DB / 接口定义 / 协议契约**，是否**涉钱/权限/数据迁移**，有哪些上下游强弱依赖。
  用搜索工具摸清现状与调用链。
- **抄近邻**：在目标仓库的设计文档目录（先找 `docs/design/`、`docs/specs/`、`docs/adr/`、
  `rfcs/` 这类约定目录，找不到就问用户）找 **1–2 篇同子系统的既有文档**当结构与措辞样板。
  房子风格照它们走；一篇都没有就用 `assets/proposal-template.md` 的骨架。

### 1 · 定深度 + 裁章节

**深度自动判定**（用户可一句话覆盖，如"写详细点/按重型来/轻量即可"）：

| 档 | 触发条件（满足更高档的任一项即升档） | 骨架 |
|---|---|---|
| **轻量** | 单包、无 DB/接口变更、纯前端交互/文案/小重构/单点 bug 修 | 背景&目标(含非目标) → 方案 → 测试计划 → 风险与对策 → WBS → 待拍板 |
| **标准** | 跨 1–2 包，或动 1 张表 / 1 个接口 / 1 处契约 | 必备 11 节主干（见 `references/section-model.md`） |
| **重型** | 跨 3+ 包 / 新增表 / 多接口 / 动跨层契约 / 涉钱·权限·数据迁移 | 必备 11 节 + 加分项（选型对比 / 兼容性 / 灰度回滚 / 监控 / 依赖矩阵 / 分阶段实施） |

**分层裁剪**：按第 0 步探测到的层，只保留对应章节，其余不写（不留空章节）。映射矩阵见
`references/section-model.md`（前端→UI/组件/埋点/性能；server→DB/接口/存储/监控/上线回滚；
协议/SDK→契约/事件流/双向兼容；跨层→全链路数据流 + 契约对齐）。

> 判完深度和章节，**先把最终大纲（含每节一句话要点 + 一段执行摘要草稿）报给用户确认**，
> 再逐节展开。大纲就是金字塔骨架——先对齐骨架能避免整篇跑偏后返工。

### 2 · 逐节起草

逐节按 `section-model.md` 写"这节该放什么"，**每节第一句先给结论**再展开论证；背景与目标
一节走 **SCQA** 序言（见 `pyramid.md`）。每节都守高密度铁律（见下）。**画图前先想清"这张图
要让评委秒懂哪句话"**，再按 `diagram-cookbook.md` 的 message-first 三步选图型；达阈值必画
（调用链对象>3→时序图；实体状态>3→状态机；User>1&UseCase>5→用例图），小图用 ASCII。

### 3 · 自检 lint 门禁（不过不算完成）

草稿完成后，**对照 `review-checklists.md` 逐条自检**：评审反模式 lint + 12 项收尾自检 +
通过口径；再补跑两项结构门禁——`pyramid.md §六`（金字塔/突出重点）与
`diagram-cookbook.md §七`（图表）。命中即修，确实不适用的显式说明理由。这一步是
"拉评审就绪"与"草稿"的分界线——跳过它等于把挑刺工作推给评委。

中/重型方案在自检后再加一道**独立批判反思**：起一个只拿「用户需求 + 草稿」的
全新上下文子代理（不带你的取材过程与偏好），让它攻击四个维度——需求覆盖完整性、
知识获取充分性（依赖库/组件 API 是否查过而非假设）、知识应用正确性（文件路径/字段
是否验证存在）、方案可行性（漏洞、过度设计、不必要的改动）。每条攻击要么修、要么
显式驳斥并记进「待拍板事项」。

### 4 · 产出与发布

**先本地 md 草稿 → 再经 report 适配器发布**（保真、可版本管理、可重跑）：

1. md 存到目标仓库的设计文档目录（第 0 步探测到的约定目录；没有就用 `docs/design/`，
   命名 `YYYY-MM-DD-<topic>-design.md`，日期用**今天**）。
2. `report.type=markdown`（默认）：报告即这个 md 文件，路径回给用户。
   `report.type=lark-docx`：按 fix-report 的同一发布通道导入为在线文档——**先问用户落到
   哪个知识库节点/文件夹**再导。
3. **关键图有条件就升级成白板**：目标环境有画图工具（如 `lark-cli board` 或仓库自带
   whiteboard 工具）时，数据流总图/架构分层/核心状态机/产品全景这类关键图按 ASCII 蓝图
   画成白板再嵌入；md 里 ASCII 蓝图作为可 diff 的同源真源保留。没有白板通道就保留
   ASCII——不阻塞交付。
4. 回链接/路径给用户。

### 5 · 拉评审收尾

产出后确保三件到位（缺了就不是"拉评审"文档）：

- **待团队拍板 agenda**：把这次评审真正要拍的决策显式列成 `Q1…Qn`。
- **评审记录占位表**：评审人 / 结论(通过·条件通过·不通过) / 时间 / 遗留 TODO。
- **TODO**：每条带**唯一跟进人 + DDL**。

顺带提醒评审节奏：**评审前一天**把文档发评审群预读（有 notify 适配器时可代办）。

## 高密度写法铁律（每节都守）

违反下列任一条，评审都会打回：

- **结论先行 + 突出重点**（金字塔）：文档开头一段**执行摘要**（3–5 行讲清
  做什么/为什么/影响面/要拍什么）；每节第一句给结论；**章节标题本身携带结论**
  （写"用 provider 抽象替换 3 处硬编码"，不写光秃秃的"方案设计"）；关键结论加粗、
  变更点 `⬅` 标注、推翻性判断用 `> ❗` 聚光。自检：只读执行摘要 + 各节标题 +
  每节 `> 一句话`，能不能拼出完整故事。
- **量化一切**：把"低延迟/大幅提升/很多"换成数字（"P99 从 800ms→200ms"
  "+50% 承接 300QPS"）。现状盘点必须带真实数字。
- **每个设计决策配"为什么"**：DDL/接口/取舍后面跟一段**设计要点**讲清为什么这么选、
  为什么不那么选。
- **结构用表/图/代码块承载 + 一图一结论**：概念用表、流程用图、DDL/类型/接口用代码块，
  避免大段纯文字。画图先想清"这张图要证明哪句话"，每张图正下方补一句图注结论；
  代码/DDL 块后紧跟一行 `> …` recap 要点。
- **一张巨图 → 拆成分层图**：总览框图（框≤7）+ 分模块细图逐层展开；已有系统迭代就
  copy 旧图并**显眼标注变更点**（加粗/`⬅`）。
- **非目标必写**：先圈掉这次**不做什么**、哪些**延后**（用 ✅ 做 / ⏭️ 延后 / ❌ 不做
  标注范围）。
- **同一概念全程同词**：新词首次出现即解释；禁同词多义 / 多词同义
  （跨 PRD/接口/DB/代码/文档保持一致）。
- **异常链路不能只画正常路**：异常/边界通常占 40%+，每个异常点给处理机制
  （超时/失败/一致性/回滚）。
- **零客套**：不写"综上所述""众所周知"这类填充；`> 一句话：…` 用来收束要点。
