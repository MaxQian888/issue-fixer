# 判定报告格式与实例

claim-verify-first 第 3 步的输出模板。用户要的是证据链，不是态度。

## 三段式

```
判定：<是问题 / 不是问题 / 已修复 / 证据不足>
证据：<file:line> + 关键代码 + 推理链（触发条件 → 路径 → 错误行为）
动作：<已修复（file:line）/ 工作区不动 / 建议下一步>
```

多条命题逐条列，不合并成一锅结论。

## 实例

**论断**（来自 review 评论）：`getListRequestKey` 中 `statusFilter` 为 `string` 类型且
不等于 `'all'` 时，`[...options.statusFilter]` 会把字符串拆成字符数组，而非单元素数组。

**取证**：读当前文件 → `statusFilter` 类型确实是 `string | string[]`；`[...string]` 在
TS 中按迭代器展开为 `string[]` 字符 → 命题成立。

**判定**：是问题。

**动作**：修为 `Array.isArray(f) ? f : [f]` 等价写法，回归用例覆盖字符串入参。

---

**反例**：另一条评论称"首屏缓存 revalidate 分支会先清空列表"。取证后发现清空只发生在
`pageUpdateMode='revalidate'` 且 `currentPage === 1` 的分支，评论把两个分支混为一谈 →
**判定：部分成立**（条件描述错，但 replace 分支吞掉 revalidate 的问题真实存在）→ 只修
成立的那半。

教训：评论的**条件**和**结论**要分开验证，常出现"结论对、条件错"或反之。

## 常见误报模式

- 评论基于旧 commit，最新代码已修 → 先对版本再取证。
- 静态扫描报"未使用"但实际被动态引用（按名拼接的环境变量、字符串注册表）→ 查拼接/
  反射用法再判。
- 把测试预期行为当成产品 bug → 先读 spec 的意图。
