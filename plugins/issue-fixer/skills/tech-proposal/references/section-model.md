# 章节模型 · 逐节写什么 + 分层裁剪矩阵

> 起草前读本文。先按「三档骨架」定大纲，再按「分层裁剪」删掉不涉及的层，最后照「逐节写什么」填内容。
> 所有章节都服从 SKILL.md 的高密度铁律：结论先行、量化、每决策配为什么、非目标必写。
> **金字塔落地**（见 `pyramid.md`）：文档头部信息表后写一段**执行摘要**（3–5 行）；每节标题下第一行给 `> 一句话：<本节结论>`；章节标题本身携带结论。图按 `diagram-cookbook.md` message-first 选型。

---

## 一、三档骨架

用户可覆盖档位。升档规则见 SKILL.md（满足更高档任一条件即升档）。

### 轻量（单包 / 无 DB·接口 / 前端交互·文案·小重构·单点 bug）

```
0  头部信息表（精简：需求 / owner / 关联 PRD / 日期 / 范围）
0.5 执行摘要（1–3 行：做什么 / 为什么 / 要不要拍板）
1  背景与目标（含非目标）
2  方案（现状一句话 + 改动点 + 关键设计要点）
3  测试计划
4  风险与对策
5  工作量（WBS，责任到人）
6  待团队拍板（若无待决项写「无，直接实现」）
```

### 标准（跨 1–2 包 / 动 1 表 · 1 接口 · 1 契约）—— 必备 11 节主干

```
0  头部信息表
0.5 执行摘要（3–5 行：做什么 / 为什么 / 影响面 / 要拍什么 → 指向 §11）
1  背景与目标（SCQA 序言：现状带数字 + 非目标 ✅/⏭️/❌）
2  关联文档（PRD / 设计稿 / 协作方方案 / 时间节点）
3  方案主体：3.1 系统现状（架构/数据流图）· 3.2 方案设计（按阈值配图）
4  接口 / 协议定义（若动接口）
5  存储设计（若动 DB）
6  监控与报警（明确阈值）
7  上线与回滚（顺序 / 依赖 / 一键开关）
8  工作量与排期（WBS 2–3PD/项、责任到唯一人）
9  验收标准（可量化、明确验收人）
10 风险与对策（成对）
11 待团队拍板 + 评审记录占位
```

### 重型（跨 3+ 包 / 新表 / 多接口 / 动跨层契约 / 涉钱·权限·数据迁移）

标准 11 节 + 下列加分项（按需插入对应位置）：

```
+ 术语说明（引入新概念时）
+ 技术选型对比（多方案表：设计 / Pros / Cons / 结论 + 为什么）
+ 概念模型（实体关系表 + ER 图）
+ 全链路数据流（跨层 ASCII 图，标服务/包边界）
+ 双向兼容性设计（逻辑·数据·接口·消息体·缓存 5 面自查）
+ 灰度方案（分批节奏 1%→10%→50%→100% / 白名单）
+ 强弱依赖矩阵（标强/弱依赖 + 降级熔断限流）
+ 可观测性分层（log / metrics / tracing）
+ 分阶段实施（Phase 1..N，每阶段可独立验证）
+ 资损考量 / 对账 / 幂等设计（涉钱必写，见 review-checklists.md §资损）
+ 成本评估（新增机器/数据中心，结论用"劣化 ¥xx/月"）
```

## 二、分层裁剪矩阵（探测到哪层就保留哪组章节）

第 0 步探测出的"层"对应到章节组。**只写探测到的层**；没探测到就不写（不留空章节）。

| 探测到的层 | 必写强化点 | 可省章节 |
|---|---|---|
| **前端应用** | UI 形态/组件划分 · 埋点 · 性能（首屏/交互指标） | 存储、IDL、上线回滚的存储段 |
| **服务端 / API** | 接口定义 · DB · 存储选型 · 监控告警 · 上线回滚顺序 | UI 节 |
| **SDK / 协议 / 跨进程契约** | 契约定义 · 事件流 · **双向兼容**（逻辑/数据/接口/消息体/缓存）· 版本协商 | UI、存储 |
| **执行器 / worker / 后台任务** | 调度 · 重试/幂等 · 资源隔离 · 失败兜底 | UI、前端性能 |
| **跨层全链路** | 全链路数据流图（框=包/服务，线=流向）· 契约对齐表 · 分阶段实施 | ——全保留 |
| **涉钱 / 权限 / 数据迁移** | 资损·幂等·对账节 · 权限模型节 · 迁移/回滚数据方案 | ——不可裁剪 |

> 裁剪判断拿不准时宁可升一档——评委对"漏了该写的"比"多写了"敏感得多。

## 三、逐节写什么（标准 11 节逐条）

### 0 头部信息表

`| 需求 | owner | 评审人 | 关联 PRD/设计稿 | 日期 | 状态 | 范围 |`

- 状态：草稿 / 评审中 / 已通过（条件通过须注待补项）。
- 范围一句话：写"只做 X，不做 Y"——评审最先看的就是边界。

### 0.5 执行摘要

`pyramid.md §三·文档级` 的 4 行块：**做什么 / 为什么 / 影响面 / 要你拍**。

### 1 背景与目标

- **SCQA 序言**（见 `pyramid.md §二`）：S 现状事实带数字 → C 冲突/痛点 → Q 待解问题 → A 一句话方案。
- **非目标三档**：✅ 本次做 / ⏭️ 延后到（写清后续版本或条件）/ ❌ 明确不做（防范围蔓延）。评审被打回的第一大原因就是边界含糊——把"不做"写死，评审才敢放。

### 2 关联文档

PRD / 设计稿 / 上游方案 / 时间节点表。只有链接没摘要等于没写——每条配一句话"这份文档里与本方案相关的点是什么"。

### 3 方案主体

#### 3.1 系统现状

- **带数字的现状盘点**：现有架构图 + 当前指标（QPS/延迟/数据量/包数），不是"目前系统比较稳定"这类空话。
- **痛点映射**：现状的哪个结构导致了本次问题——C（冲突）要能落到具体组件/调用上。

#### 3.2 方案设计

- **先给结论**：选了哪个方案、一句话为什么（不是罗列备选）。
- **改动点列表**：每个改动点标 `⬅ 新增` / `⬅ 改动` / `⬅ 删除`，评委一眼看到 diff。
- **设计要点**：每个关键决策后紧跟"为什么这么选、为什么不那么选"。这是"零成本上手"的核心——接手人读设计要点就能复述你的推理。
- **配图**：按阈值（见下）和数据流/分层模板画，一图一结论。

### 4 接口 / 协议定义（若动接口）

- 每个接口给完整签名/IDL 块（字段注释 + 枚举值 + 错误码），**禁裸 dict/any**。
- 兼容性声明：新增/改动/废弃字段，老版本消费方会不会挂。
- 块后紧跟 `> …` recap（如 `> 本接口幂等靠 clientRequestId，服务端去重窗口 24h`）。

### 5 存储设计（若动 DB）

- 表 DDL / 字段含义 / 索引（最左匹配、不重复建）/ 量级与分片预估。
- **数据迁移与回滚**：存量数据怎么搬、回填失败怎么办、回滚是否留脏数据。
- 加表还是改表要给结论 + 为什么。

### 6 监控与报警

- 核心链路业务打点清单（指标名 + 维度）+ 报警阈值。
- metrics tag 低基数可枚举（百以内）——高基数 tag 会封禁/刷屏。

### 7 上线与回滚

- **上线顺序**：存储变更 → 权限申请 → 下游依赖发布 → 配置变更 → 代码变更。
- **一键开关**：有风险的改动必须全收敛进开关。
- **回滚覆盖**：系统/接口/配置/数据四面，回滚后不留脏数据。

### 8 工作量与排期（WBS）

- 每项 2–3PD 粒度，责任到唯一人，含部署/同步/回滚辅助任务（最容易漏的）。
- 有依赖的先标关键路径。

### 9 验收标准

- 可量化、可观测（"P99 < 200ms"、"覆盖率 ≥80%"，不是"功能正常"），明确验收人。

### 10 风险与对策

- **成对出现**：每条风险配一个对策，只有风险没有对策等于把雷留给评委。
- 按维度归类（工程/安全/稳定性），按程度排序（最可能炸的在前）。

### 11 待团队拍板 + 评审记录占位

- **Q1…Qn agenda**：每个待决项给**你的倾向结论 + 备选**，别让评委从零想（见 pyramid.md §五 Q 的写法）。
- **评审记录占位表**：`| 评审人 | 结论 | 时间 | 遗留 TODO |`。
- **TODO**：每条唯一跟进人 + DDL。

## 四、重型加分项写法要点

- **技术选型对比**：多方案表（设计/Pros/Cons/结论+为什么）——罗列不给结论是打回项。
- **双向兼容 5 面自查**：逻辑（新旧代码互认）/ 数据（新旧格式互读）/ 接口（新旧版本互调）/ 消息体（新旧事件互解析）/ 缓存（新旧 key 互见）。逐面写结论，别只写"兼容"。
- **灰度方案**：分批节奏 + 白名单 + 每批的观察指标与回退触发线。
- **分阶段实施**：每阶段可独立验证、可独立回滚，写清阶段间的依赖与验收。
- **资损/幂等**：见 `review-checklists.md §资损`——涉钱方案没有幂等设计就是一票否决。
