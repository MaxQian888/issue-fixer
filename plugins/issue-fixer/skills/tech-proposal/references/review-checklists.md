# 评审自检门禁 · 反模式 lint + 自检清单 + 通过口径

> SKILL.md 第 3 步用。草稿写完后**逐条自检**：先扫 17 反模式（命中即修），再过 12 项收尾自检，再跑金字塔/图表结构自检，再按维度 checklist 查专项，最后核对通过口径。
> 这一步把"草稿"变成"拉评审就绪"。跳过它等于把挑刺推给评委。

---

## 一、17 条评审反模式 lint（命中会被打回，逐条自查）

1. **背景没讲清就进方案** → 技术评审沦为需求评审。修：背景补事实/数据，让非本模块的人也读得懂。
2. **目标不可量化**（"大幅提升 QPS""低延迟"）→ 换成数字 + 预期收益。
3. **只画正常链路**，异常/边界缺失（异常常占 40%+）→ 每个异常点补处理机制（超时/失败/一致性/回滚）。
4. **多方案罗列但不给结论**（"A 不错 B 也行"）→ 每个选型给明确结论 + 为什么。
5. **接口缺定义**：缺接口名/出入参/枚举值、无注释、裸 dict → 补齐定义 + 字段注释 + 错误码。
6. **无监控 / 无回滚 / 无自测** 却硬上 → 三板斧（可灰度·可监控·可应急）缺一不可。
7. **改存储 schema 但没做前后兼容、没 Rollback** → 补双向兼容自查 + 数据回滚方案。
8. **一张巨图堆所有细节** / 先上 3 屏表格再讲干什么 → 拆分层图；结论先行。
9. **WBS 粒度粗、无唯一责任人、漏辅助任务** → 拆到 2–3PD、责任到唯一人、补部署/同步/回滚任务。
10. **同词多义 / 多词同义 / 引入新概念不解释** → 全程统一术语，新词首现即解释。
11. **涉钱不做幂等 / 不落补偿标记 / 无一键开关** → 见 §资损。
12. **metrics tag 高基数** 导致被封禁、报警噪音刷屏 → tag 低基数可枚举（百以内）。
13. **方案阶段贴大段实现代码** → 只给伪代码/接口签名/DDL，不贴实现。
14. **保留空章节不删 / 幽灵章节**（"参考资料"却是空的）→ 不适用的章节直接删；引用就近给出。
15. **结论埋在段落里 / 标题是哑名词 / 无执行摘要**（金字塔）→ 加执行摘要、每节结论先行、标题携带结论（"方案设计：用 X 替换 Y"而非"方案设计"）。见 `pyramid.md`。
16. **同层分组不 MECE**：几条其实是一条的不同说法（不独立）/ 漏了一种情况（不穷尽）→ 归类分组：非目标分 ✅/⏭️/❌、风险按 工程/安全/稳定性、异常链路不遗漏。
17. **该画图处堆文字 / 图无结论 / 该上白板的关键图只有 ASCII / 堆无效 mermaid**（用图表说话）→ 达阈值必画、一图一结论、关键图有条件升级白板、mermaid 换 ASCII 或白板。见 `diagram-cookbook.md`。

## 二、12 项收尾自检（当门禁逐条打勾）

1. Required 部分是否完成，或有充分理由跳过？
2. 背景清晰完整，其他角色无障碍读懂？
3. 目标可量化可观测、有预期收益数字？
4. 架构变更部分有**显眼标识**？
5. 技术选型明确，"有无更好选型"已讨论？
6. 接口变更给出完整定义？
7. WBS 每项有**唯一负责人和交付时间**（含合作方）？
8. 机器资源是否需预估申请？
9. 有 case 和步骤在上线后验证？
10. 发布失败能否顺利回滚且不影响线上数据？
11. 监控/告警/日志是否调整、对稳定性影响是否考虑？
12. 跨机房/跨集群数据传输或请求是否评估？（一般 N/A，除非真有）

> 总判据：**换个人照文档能零成本上手**。做不到就还没写完。

## 二·补、金字塔 + 图表结构自检（跑完 12 项再跑这两组）

- **金字塔 / 突出重点**（`pyramid.md §六`）：有执行摘要（3–5 行）· 每节结论先行 · 标题携带结论（过「读标题即读全文」测试）· 背景走 SCQA · 同层分组 MECE · 组内单一逻辑顺序 · 重点靠版式跳出 · 零客套。
- **图表**（`diagram-cookbook.md §七`）：达阈值的图都画了 · 一图一结论 · 无巨图堆细节 · 主流程 ≤8 步 · 异常/分支有图 · 迭代图标了变更点 · 图例统一 · 关键图有条件升级白板（小图 ASCII，无无效 mermaid）。

## 三、分维度评审 checklist（reviewer 视角，按改动命中查）

### 接口 / 协议

命名规范（驼峰首字母大写）· 字段注释 + 枚举值 · 兼容老版本 · 特殊字段单位 · 禁裸 dict · 限流评估 · QPS 预估。

### 存储 / DB

量级/分片 · 必要索引（不重复建、最左匹配）· 大 key/热 key · 存储型 vs 缓存型 · 主从延迟 · key 逐出 · 多机房禁自增主键 · 下游 schema 对齐 · 敏感字段加密。

### 缓存

大 key/热 key · 主从延迟 · 存储型 vs 缓存型 · key 逐出策略。

### 安全

垂直/水平越权 · SSRF · SQL 注入 · 敏感数据脱敏 · 登录态/鉴权/反爬反作弊 · CSRF。

### 监控告警

核心链路业务打点 + 报警规则 · 明确阈值 · 监控可冗余不可噪音 · metrics tag 低基数可枚举。

### 灰度 / 回滚（三板斧：可灰度·可监控·可降级应急）

资损风险必须一键开关且改动全收敛进开关 · 灰度分批（尾号/白名单 1%→10%→50%→100%）· 回滚覆盖系统/接口/配置/数据。

### 上线顺序

存储变更 → 权限申请 → 下游依赖发布 → 配置变更 → 代码变更 · 客户端/跨包接口是否需先合入（否则 block 下游）。

### 资损 / 对账 / 幂等（**涉钱必查**，否则一票否决）

- 「有价资源流动」（奖励下发/补偿/积分卡券/转账扣款结算）必做**幂等设计**；幂等 key 优先端上传入且必填校验。
- 补偿必须**落补偿标记**（单独状态或扩展字段）。
- 资金口径："出款慎失败、入款慎成功"；金额单位全系统统一。
- 对账方案 + 资金巡检。

## 四、图表阈值（硬约定，达阈值必画）

| 图 | 触发阈值 |
|---|---|
| 用例图 | UseCase > 5 且 User > 1 类 |
| 时序图 | 单次调用链对象 > 3（复杂需求按角色拆多张） |
| 状态图 | 单实体状态 > 3 |
| 活动图 | 协作对象 > 2 且流程复杂 |
| ER 图 | 涉及新增/改动表 |
| 全局架构图 | 跨层/跨服务（框=服务/包，线=流向） |

## 五、通过口径（生成后核对，也是评审预期）

- **默认一票否决**：任一评委判不通过即不通过，须修改后二次/多次评审；争议由各方负责人定夺。
- **结论三态**：通过 / **条件通过**（记录待补内容，最晚提测前确认）/ 不通过（说明原因重新发起）。
- **准入提醒**：跨包/动契约/新表/涉钱/新人前几个复杂需求 → 拉评审；纯改文案/图片链接/css、纯增删埋点可豁免，但须提前同步 QA 并注明理由。
