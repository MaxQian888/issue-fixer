# 规模档（S / M / L / XL）

**档**衡量的是这次改动的复杂度与风险，决定每一步做多深；它不决定哪些步骤存在。
步骤不适用只有四种来源：模式、结局（见 [outcomes.md](outcomes.md)）、门禁答复、能力缺失。
任何档都走完整流水线——S 档是"每步做到最浅的合格深度"，不是"跳步"。

档与严重度是两个轴：严重度（`sev1` 阻断 … `sev4` 轻微）描述用户影响，写进运行状态的
`severity`，影响沟通的紧迫度；档描述改动本身，影响流程深度。严重的问题可以是 S 档
（一行修掉的白屏），轻微的问题可以是 L 档（改一个间距要动设计系统 token）。

## 何时定档

1. **分诊（triage）定初档**：只凭证据与仓库结构估，标 `preliminary`。
2. **Gate ① 定正式档**：定位与方案落地后按下表重算，写进 Gate ① 卡片，经批准生效。
3. **运行中只升不降**：任何升档信号出现即 `runstate.mjs reopen <runDir> gate1 --reason
   "<命中的信号>"`，再 `meta --tier` 升档并重过 Gate ①（见"升档触发"）；熔断与结局变化
   说明定位本身可能错了，回退得更早——`reopen locate`，它同样回退并重开 Gate ①。降档同样
   只能在重开的 Gate ① 上提议、由用户确认。Gate ① 批准后不经 reopen 直接改档会被 CLI 拒绝。

每次变更都走 `runstate.mjs meta <runDir> --tier <档> --reason "<命中的信号>"`，
`tierHistory` 是升档证据。一条 tracker 记录或一句"小问题"不会把 L/XL 的改动缩成快速
修复——档只看判档表。

## 判档表——取命中的最高档

| 信号 | S | M | L | XL（出流水线） |
|---|---|---|---|---|
| 产品代码改动文件（不含测试） | 1–2 | 3–6，单包 | 7+，或跨 2+ 包 | — |
| 预估产品代码净改动行 | ≤ 30 | ≤ 150 | > 150 | — |
| 改动符号的调用方 | 1 个调用点 / 单页面 | 共享组件/工具，≥ 2 调用方 | 公共 API、SDK 导出、协议、DB schema | 跨仓库、跨团队契约 |
| 行为变化 | 只修正所报行为 | 相邻行为需同步调整；已有测试断言需改 | 对外契约变化；需迁移/兼容/开关 | 需重新定义产品行为 |
| 方案确定性 | 唯一合理改法 | 2 种改法，取舍局部 | 多种改法，取舍跨模块 | 需产品/设计决策才能选 |
| 根因位置 | 本仓、已定位 high | 本仓、medium 且需活体确认 | 本仓多处共同作用 | 不在本仓 |
| 验证可达性 | lint/单测/fixture 可证 | 需 local-dev 或多包测试 | 需集成环境/灰度才能证 | — |

**风险域直升**（命中即至少到该档，与规模无关）：

- 至少 **M**：并发/缓存/异步时序、重试与幂等、i18n 基础设施、可访问性语义、feature
  flag 默认值、构建/CI/lint 配置、依赖升级或 lockfile 变化、生成代码的源头（schema/IDL）、
  修改或删除已有测试断言、性能问题。
- 至少 **L**：鉴权/权限、计费/支付、数据迁移/删除/回填、安全漏洞、隐私或个人数据、
  跨服务协议、存储格式、对外发布的 SDK/API。

**XL** 不在本流水线里修：产出方案（`tech-proposal`）或原型（`prototype`），结局记
`escalated`，把"可以先做的最小切片"写进 Gate ① 卡片的备选方案。用户在 Gate ① 答
`changes-requested` 并选定某个切片时，流水线自动回到 `locate`：以切片为新方案重算档
（通常 M/L）、结局改回 `fixed`，再过 Gate ①。

**L 档转 `escalated`**：仓库惯例要求这类改动先经团队评审（RFC/设计评审），或用户在 Gate ①
要求先评审时，结局为 `escalated`，交 `tech-proposal` 文档；评审通过后以新 run 或
`reopen locate` 继续。

## 档 → 每步深度

所有档都执行每个适用步骤；表中是该档的**最低合格深度**。

| 步骤 | S | M | L |
|---|---|---|---|
| 取证 intake | 原文 + 证据清单 | + 缺口一次问清 | + 相关历史记录/MR/事故检索 |
| 复现 reproduce | 症状在基线上可观察（截图/报错/命令输出） | 可重复的复现命令或脚本 | 最小复现 + 触发条件边界（何时不触发） |
| 定位 locate | 两个独立锚点 | + 改动符号调用方清单 + 同类缺陷扫描 | + 数据流/时序说明 + 跨包契约 |
| 根因 | 一句因果链 | 完整因果链 + "为什么现在"（引入提交） | + 备选方案对比与取舍理由 |
| Gate ① | 紧凑卡片 | 标准卡片（含影响面、测试计划） | 方案文档（`tech-proposal` 轻量/标准）+ 回滚方案 |
| 红灯 red | UI：`before` 截图 + 实测属性；逻辑/报错/数据：有 harness 写回归测试，无 harness 用脚本化复现 | 同 S，且无回归测试时在 Gate ② 说明原因 | 失败的回归测试 + 边界用例 |
| 验证 verify | 改动面档位（见 repo-collab） | + 受影响包完整测试 | + 仓库 CI 等价的全量检查（可行时） |
| 复核 review | 自查清单；仓库 review 能力有则用 | 自查清单 + 独立上下文 `bugfix-review`；仓库 review 能力有则用 | 自查清单 + `bugfix-review` + 仓库 review 能力（可发现就必用） |
| MR 正文 | Summary / Changes / Test Plan | + 根因 + 风险 | + 回滚步骤 + 发布注意事项 |
| 熔断预算（见下） | 2 个假设 | 3 个假设 | 3 个假设，且方案级失败直接回方案 |

`e2e-check`、before/after 证据、手测提示、CI 跟进、报告在所有档都是同一契约，深度由
改动面与分类决定，不随档变浅。

## 升档触发——出现即停、升档、回 Gate ①

- 需要改动已批方案之外的文件、组件、路由或包。
- 实测调用方数、改动行数越过当前档上限。
- 命中上面的风险域。
- 发现已有测试断言了当前（错误）行为，修复要改它。
- 需要新依赖、依赖升级或 lockfile 变化。
- 熔断预算耗尽（见下；回退到 `locate` 而不是 `gate1`）。

已批方案内的行号移动、实现细节、命名不算升档。

## 熔断预算

一个**假设**是一轮"根因假设 → 预测 → 改动 → 验证"。验证没按预测变绿，就是一个失败
假设，写进 `<runDir>/hypotheses.md`（格式见 [diagnosis.md](diagnosis.md)）。

- 失败假设数达到本档预算：停止改码。把 worktree 里的试验性改动留在工作区（不提交、
  不 stash 别人的东西），`reopen locate --reason "熔断：<n> 个假设失败"`，带着假设日志
  重新定位并重过 Gate ①：定位是否错了、是否要升档、是否需要用户补充信息。
- 定位阶段两轮收窄（静态 → 动态）仍达不到 `medium` 置信度：停下问，不猜。
- Gate ② 连续两次用户手测失败：视为定位或根因可能错误，`reopen locate` 而不是继续补丁。
- CI 重跑最多一次（见 CI 步骤）；由改动引起的 CI 失败的修复计入假设预算。
