# Prototype

原型是**回答一个问题的一次性代码**。问题决定形态。

## 选分支

先识别要回答的是哪个问题——从用户的话、周边代码推断，或用户在时直接问：

- **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。做一个极小的交互式终端
  应用，亲手把状态机推过纸面上难以推理的 case。
- **"这玩意应该长什么样？"** → [UI.md](UI.md)。在同一条路由上生成几个截然不同的
  UI 变体，用 URL search 参数 + 悬浮底栏切换。

两个分支产物差异巨大——选错就浪费整个原型。问题真有歧义且联系不上用户时，默认选与
周边代码更匹配的分支（后端模块 → logic；页面或组件 → UI），并在原型顶部写明这个假设。

## 两个分支通用规则

1. **第一天起就是一次性代码，并明确标注。** 原型代码放在它实际要被用的地方旁边（紧挨它
   在打样的模块或页面），上下文才明显——但命名要让路人一眼看出是原型而非生产代码。
   一次性 UI 路由遵守项目已有的路由约定；不要发明新的顶层结构。
2. **一条命令跑起来。** 用项目现有 task runner 支持的形式——`pnpm <name>`、
   `python <path>`、`bun <path>` 等。用户必须不假思索就能启动。
3. **默认不持久化。** 状态放内存。持久化是原型要**验证**的东西，不是它该依赖的东西。
   若问题明确涉及数据库，用 scratch DB 或名字写着 "PROTOTYPE — wipe me" 的本地文件。
4. **不做打磨。** 不写测试，不写超出"能跑"的错误处理，不做抽象。重点是快速学到东西
   然后删掉。
5. **暴露状态。** 每次动作后（logic）或每次变体切换时（UI），打印或渲染全部相关状态，
   让用户看到什么变了。
6. **用完即删或吸收。** 原型回答了它的问题后，要么删掉，要么把验证过的结论折进真实
   代码——别留在仓库里腐烂。

## 完成后

原型唯一值得留下的是**答案**。把它记到耐久的地方（commit message、ADR、issue、或原型
旁的 `NOTES.md`），连同它回答的问题。用户在时这就是一段快聊；不在就留个占位，让他们
（或下一轮的你）在删原型前填上结论。
