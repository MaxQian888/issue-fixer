# 用图表说话 · message-first 选图 + ASCII 菜谱

> 来源：《用图表说话》。本文把它落成可执行的画图门禁。
> 配套：文字组织与突出重点见 `pyramid.md`；达阈值必画的硬约定见 `review-checklists.md §四`。
> 一句话目标：**每张图都在替你说一句结论**——评委看图注就知道你要讲什么，看完图就信。

---

## 一、message-first 三步选图

1. **先写图注**：这张图要让评委秒懂哪句话？写不出图注结论就别画——画了也是堆细节。
2. **按关系选图型**：见 §二的速查表。关系选错，再漂亮的图也讲不清。
3. **从图型到载体**：默认 ASCII（可 diff、可版本管理、终端/文档都能看）；配置了白板工具时把**关键图**升级成在线白板（评审现场可缩放/可当场改），md 里保留 ASCII 蓝图兜底——见 §五。

---

## 二、关系 → 图型速查表

| 你要讲的关系（图注长这样） | 选这种图 | 典型场景 |
|---|---|---|
| **流转**：谁调谁、数据往哪走 | 数据流图 / 架构分层图 | 用户操作 → 前端 → 服务端 → worker → agent 全链路 |
| **顺序**：先后步骤、时序、异步回传 | 时序图 / 泳道图 | 握手流程、任务生命周期、断线重连回放 |
| **状态**：一个实体在几个态间跳转 | 状态机 | 任务的 pending/running/blocked/done、连接的 WAITING/ACTIVE |
| **结构**：模块层级、包含/依赖关系 | 架构分层图 / 树 | 包依赖、provider 抽象分层 |
| **对比**：多方案优劣、字段一致性 | 对比矩阵表 | 选型 A/B/C、契约字段谁产谁消 |
| **分支**：if/else 走向、异常分流 | 流程图 / 决策树 | 鉴权分支、降级熔断、错误码分流 |
| **实体**：表与表、DTO 与接口映射 | ER 图 | 新增表关系、类型映射一致性 |
| **进度**：排期、里程碑、分阶段 | 里程碑 / 甘特（ASCII） | Phase 1..N 上线节奏 |

## 三、达阈值「必画」是下限，不是上限

`review-checklists.md §四` 的阈值（调用链对象>3→时序图；实体状态>3→状态机；UseCase>5&User>1→用例图；新增表→ER；跨层→架构图）是**硬下限**：达到就必须画，不画是缺陷。

但更进一步：**只要一张图能让评委少读三段文字，就画。** 评审现场时间宝贵，「一图胜千言」省下的是所有评委的理解成本。判断标准很简单——你讲这段时如果忍不住想在白板上画个框图，那这个框图就该进文档。

## 四、图表菜谱（ASCII 模板，拷贝即改）

以下模板都用 **ASCII + `→`**：高保真导入任何文档、纯文本可 diff、终端也能看。图例全文统一见 §六。

### 4.1 全链路数据流图（讲「流转」）

```
用户操作            前端应用            业务后端               执行器              Agent
   │                  │                    │                    │                 │
   │  点击「发送」 →   │                    │                    │                 │
   │                  │  POST /run/start → │                    │                 │
   │                  │                    │  create task    →  │                 │
   │                  │                    │                    │  bootstrap   →  │
   │                  │   ⇠ stream events  │   ⇠ stream log     │   ⇠ tool calls  │
```
> **图 X**：<一句话，例：一次发送穿过 4 个进程边界，事件走异步回传，无同步阻塞>

### 4.2 架构分层图（讲「结构」，框≤7 个）

```
┌─────────────────────────────────────────────┐
│              消费方 (app / server)            │  ← 只依赖 provider 接口
├─────────────────────────────────────────────┤
│         provider 抽象层        ⬅ 新增          │  ← 单一注册点
├──────────────┬───────────────┬───────────────┤
│  实现 A       │   实现 B       │  mock(测试)    │  ← 各实现
└──────────────┴───────────────┴───────────────┘
```
> **图 X**：<例：新增 provider 层后，消费方与具体实现解耦，加实现只动最底层一格>

### 4.3 时序图（讲「顺序/时序」，对象>3 必画）

```
client            sdk client         server             worker
   │                  │                  │                  │
   │ ─── send ───────>│                  │                  │
   │                  │ ── JSON-RPC ────>│                  │
   │                  │                  │ ── spawn ───────>│
   │                  │<── started ──────│                  │
   │<── onEvent ──────│                  │<── result ───────│
   │                  │<── completed ────│                  │
```
> **图 X**：<例：一次调用从发起到完成的关键消息序列，标出双向兼容需要保留的两个事件>

### 4.4 状态机（讲「状态」，单实体态>3 必画）

```
        start          interrupt
 [idle] ────> [running] ────────> [interrupted]
                 │                      │
                 │ finish       resume  │
                 v                      │
            [completed] <───────────────┘
```
> **图 X**：<例：任务五态流转；⚠ interrupted→resume 当前不回放终态，是本方案要补的缺口>

### 4.5 流程图 / 决策树（讲「分支」，异常分流必画）

```
收到请求
   │
   ├─ 参数非法? ──是──> 返回 400 + 打点
   │
   ├─ 已注册? ───否──> 返回 404 + 打点
   │
   └─ 是 ──> 执行 ──成功──> 200
                  │
                  └─失败──> 重试 1 次 ──仍败──> 告警 + 返回 502
```
> **图 X**：<例：分支决策覆盖全部异常路径；每条异常路径都有处理机制>

### 4.6 对比矩阵表（讲「对比/选型」）

```
| 方案 | 设计 | Pros | Cons | 结论 |
|------|------|------|------|------|
| A 直改 | 就地改 3 处 | 改动小 | 下次还要改 | ❌ 治标不治本 |
| B 抽象层 | 收敛注册点 | 一次到位 | 多一层间接 | ✅ 选它，因为… |
```
> **图 X**：<例：B 的一次性成本换来后续零散弹改动>

### 4.7 ER 图（讲「实体关系」）

```
┌──────────┐ 1      n ┌──────────┐
│  project │─────────<│   task   │
└──────────┘          └──────────┘
                             │ 1
                             │
                             n
                      ┌──────────┐
                      │   step   │
                      └──────────┘
```
> **图 X**：<例：task 挂在 project 下，step 挂在 task 下——删掉 project 级联到哪层是本方案要拍的>

## 五、载体双轨：ASCII 当蓝图，白板当评审门面

**评审是给人看的**——白板在现场能缩放、能顺着讲、能当场改，比文档里的 ASCII 好读得多。但白板不好 diff、不好版本管理，所以**md 源里保留 ASCII 蓝图**作为可 diff 的真源与兜底。两条轨道各司其职：

| 图的角色 | md 源（可 diff 真源） | 评审文档 | 用什么工具画 |
|---|---|---|---|
| **关键图**：全链路数据流总图 · 架构分层图 · 核心状态机 · 产品全景 | ASCII 蓝图 | **有白板通道就升级成白板**（首选） | 配置的白板工具（如 `lark-cli board`） |
| **次要图**：小流程 · 对比矩阵 · ER 小图 · 泳道 · 里程碑 | ASCII | ASCII 原样（文档代码块高保真） | 直接写进 md |
| **Mermaid** | 尽量不用 | ⚠️ 多数在线文档不渲染，只当代码块 | 要正式图就上白板，别靠 mermaid |

**ASCII → 白板联动流程**（关键图走这条）：

```
① md 里先把 ASCII 蓝图画对（关系、方向、图注都定稿）
② 有白板通道时，按蓝图在在线白板上画成正式图
③ 评审文档嵌白板；md 里 ASCII 蓝图继续当真源
④ 蓝图改动时白板跟着改——别让两个版本漂移
```

## 六、图例统一约定（全文一套，别发明第二套）

| 记号 | 含义 |
|---|---|
| `→` | 同步调用 / 数据流向 |
| `⇠` | 异步回传 / 事件流反向 |
| `⬅ 新增` / `⬅ 改动` | 本次变更点（迭代已有系统必标） |
| `[ ]` | 状态 / 节点 |
| `│` `─` | 连接 / 边界 |
| `⚠` | 已知缺口 / 本方案要补的点 |
| `> **图 X**：` | 图注结论（每张图必须有） |

## 七、图表自检（并入第 3 步 lint 门禁）

- [ ] **达阈值的都画了**（见 §三硬下限），**该画的也都画了**（讲这段时你想在白板上画的那个框图进文档了）。
- [ ] **一图一结论**：每张图都有 `> **图 X**：<结论>` 图注，评委看图注就知道你要讲什么。
- [ ] **无巨图堆细节**：框≤7，超了就拆分层（总览图 + 分模块细图）。
- [ ] **主流程 ≤8 步**：超了拆分层（人一眼能跟的步数就这么多）。
- [ ] **异常/分支有图**：不只画正常链路，异常路径在图上找得到处理。
- [ ] **迭代图标了变更点**：`⬅ 新增`/`⬅ 改动` 显眼标注。
- [ ] **图例统一**：全文一套记号，没有第二套自创记号。
- [ ] **载体选对**：有白板通道时关键图已升级白板；md 里保留 ASCII 蓝图同源；没有不渲染的无效 mermaid。
