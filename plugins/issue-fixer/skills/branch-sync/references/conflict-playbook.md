# 冲突处置手册

branch-sync 第 4 步的分类型处置。只在出现冲突时读。

## 决策顺序

每个冲突文件先问一个问题：**双方改动是叠加关系还是互斥关系？**

- 叠加（各加导出/case/段落/配置项）→ `都保留`，不询问。
- 互斥（同一行改了两个值、同一函数两种实现、一边删一边改）→ 判断不了就列入确认清单。

## 按文件类型的固定处置

| 文件 | 处置 |
|---|---|
| lockfile（pnpm-lock / package-lock / yarn.lock / Cargo.lock / go.sum） | 不手合。接受任一边后 worktree 内重跑仓库安装命令重新生成；依赖项冲突以基线侧为准再装回我方新增依赖 |
| 生成产物（auto-generate/、proto 产物、dist） | 接受一边后跑对应生成命令重建，不手改 |
| `OWNERS` / `AGENTS.md` / CI 模板 | 通常是叠加 → `都保留` |
| `CHANGELOG.md` | changeset 维护，不手编；冲突时保留双方条目按时间序 |
| 同函数被双方改写 | 逐语义对比：我方版本 + 基线新增逻辑能否共存；能则手动合并，不能则列入确认 |
| 基线删了我方引用的代码 | 语义冲突 → 必问（保留代码要同步改引用，删代码要确认我方功能可弃） |
| 基线新增文件与我方同名新文件 | 看内容意图；同名不同实现 → 确认 |

## 操作细节

- 单边确定正确时才用 `git checkout --theirs/--ours <file>`；多数文件手动合。
- 合完一个文件：`git add <file>` + `git diff --check` 扫残留 `<<<<<<<` / `>>>>>>>`。
- 一批冲突合完先跑仓库安装命令（若 lock/package 元数据被动过）再 `git rebase --continue`。
- 连续多个 commit 撞同一文件：第一次就合对，后续 commit 的冲突通常会变小。
- 全部解决后对照 `git log origin/<base>..HEAD --oneline` 确认我方 commit 序列完整、无丢失。

## 确认消息模板

```
rebase 到 origin/<base> 有 N 处需拍板（其余 M 处已按"都保留"自动合）：
1. <file>: <冲突是什么> — 推荐 <方案>，因为 <依据>
2. ...
```

一次问完；回复后直接执行，不二次确认。
