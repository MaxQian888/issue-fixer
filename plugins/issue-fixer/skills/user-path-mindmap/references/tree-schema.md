# tree.json 结构与编辑规范

`tree.json` 是脑图的唯一手写源。仓库自有的生成器读它出派生图（如
`diagram.json`）；CI/治理脚本也读同一份做门禁与报表。字段既给看图的人
（chain/flow/label/角色配色），也给机器看的治理意图（`p` 优先级 / `spec`
归属测试）。

> 本文描述的是通行 schema；目标仓库的校验器（`mindmap.lintCommand` 指向的脚本）
> 才是契约。字段取值、优先级集合、spec 解析根以该校验器当前定义为准。

## 顶层结构

```jsonc
{
  "root":   { "label": "..." },                 // 中心根节点
  "colors": { "<key>": "#RRGGBB" },             // 每个一级模块一个色 key
  "legend": [{ "role": "entry", "label": "入口" }, ...],
  "branches": [                                  // 一级模块（① ② ③ …）
    {
      "id": "b-xxx", "label": "① 模块名", "color": "<colors 里的 key>",
      "functions": [ /* 功能节点，见下 */ ]
    }
  ]
}
```

## 功能节点（functions[] 的一项）

```jsonc
{
  "id": "f-xxx",              // 唯一 id
  "label": "功能名",           // 功能盒文字
  "p": "P0",                  // 可选：CUJ 优先级；合法值以仓库 validator 为准
  "spec": ["tests/e2e/x.spec.ts"], // 可选：owning spec；由仓库 validator 按支持的测试根解析
  "chain": [ ... ]            // 线性链路；或改用 flow（二选一）
  // "flow": { ... }          // 扇出→合流链路（含 branches / next / 循环）
}
```

`p`/`spec` 是人工维护的治理意图，图生成器不消费它们；仓库 validator、门禁与
报表消费它们。

## chain（线性链路）

```jsonc
"chain": [
  { "l": "第一步文字", "r": "entry" },
  { "l": "中间步骤" },                 // r 省略：非首非尾默认 step
  { "l": "结果", "r": "result" }
]
```

- `l` = 节点文字，`r` = role（着色）。`r` 省略时：第一项默认 `entry`、最后一项
  默认 `result`、其余 `step`。
- chain 节点也可带 `key` / `loopTo`（见「循环」）。

## flow（扇出 → 合流）

```jsonc
"flow": {
  "l": "入口文字", "r": "entry",
  "key": "anchor1",                          // 可选：登记回环锚点
  "branches": [                              // 并列分支（扇出）
    { "l": "选项A", "r": "option" },
    { "l": "选项B", "res": "对应结果", "r": "option", "loop": true }  // res=情况→结果；loop=结果回连入口成小循环
  ],
  "next": {                                  // 分支合流后继续（链表，可递归 next）
    "l": "合流后继续", "r": "step",
    "loopTo": "anchor1",                     // 可选：本节点回连到某 key 锚点
    "next": { "l": "结果", "r": "result" }
  }
}
```

- `branches[]` = 扇出，随后 `next` 合流回主干（多→一）。
- 分支的 `res` = 「情况 → 对应结果」，不合流；`res` + `loop:true` = 该结果回连
  到 flow 入口（小循环）。
- `next` 是链表，可一路 `next` 下去，也可在中间再挂 `branches`。

## 角色（role）配色

| role | 语义 |
|---|---|
| `entry` | 入口 |
| `step` | 步骤 |
| `option` | 可选项 / 分支 |
| `result` | 结果 |

连线颜色随所属一级模块色；分支扇出后汇聚回主干（多→一连线）。

## 循环（loop）—— 两种写法

1. **锚点回环**：在某节点写 `"key": "foo"` 登记锚点；在后面某节点写
   `"loopTo": "foo"` 回连过去。chain / flow 通用。用于「一轮结束 → 出队 →
   新一轮 ↺」「WAITING → 休眠 → 唤醒 → 回 WAITING ↺」这类主干回环。
2. **分支结果回入口**：在 `branches[]` 某项写 `"loop": true`（配合 `res`），
   让「该情况的结果」回连到 flow 入口。用于「允许 → 下一步再弹 ↺」
   「否·调整 → 重出确认卡 ↺」这类小循环。

普通连线与回环连线在图上应可视觉区分（如 bottom→bottom 回环）。

## 轮次（turn semantics）标注规范 —— 别把三类循环画成同一个 ↺

同一个「↺」在实现里可能是三类**完全不同**的循环，标 label 时要写清是哪一类
（否则脑图会误导，也和代码对不上）：

| 记号 | 含义 | 判据 | 例子 |
|---|---|---|---|
| **T · 新回合** | 每次迭代都新起一个回合/turn | 代码每轮调用一次「开始新回合」入口 | 会话内追问·排队（每条=1 新回合，串行） |
| **W · 同回合内** | 重复在**一个回合内部**、不新起回合 | 一次调用/一个回合内翻页或逐项确认 | 多问翻页；逐项权限弹窗；同一规划回合内重出确认 |
| **P · 客户端轮询** | 纯定时轮询，**没有**业务回合 | `setInterval`/`setTimeout` 轮询 | 状态查询、断连检测、就绪等待 |

在 label 里直接点明类别，例如：`"工具执行→下一项再弹 ↺ (同一回合内·W)"`、
`"状态轮询 (客户端轮询·P)"`。轮数、间隔、超时和平台差异都必须在本次修改时
从代码核实；不要把本文示例当作现行数值。

## 可复制的最小示例

**① 加一个线性（chain）功能节点**——放进某模块的 `functions[]`：

```jsonc
{
  "id": "f-xxx", "label": "新功能名",
  "chain": [
    { "l": "入口动作", "r": "entry" },
    { "l": "中间步骤" },
    { "l": "结果", "r": "result" }
  ]
}
```

**② 加一个扇出→合流（flow）功能节点**：

```jsonc
{
  "id": "f-yyy", "label": "带分支的功能",
  "flow": {
    "l": "入口", "r": "entry",
    "branches": [
      { "l": "选项A", "res": "A 的结果", "r": "option" },
      { "l": "选项B", "r": "option" }
    ],
    "next": { "l": "合流后继续", "r": "step", "next": { "l": "结果", "r": "result" } }
  }
}
```

**③ 给现有 flow 加一个分支**——往 `branches[]` 里加一项：

```jsonc
{ "l": "新分支", "res": "新分支结果", "r": "option" }
```

**④ 加循环（三种写法，对应三类轮次）**：

```jsonc
{ "l": "每轮结束 → 出队 → 新回合 ↺ (T·新回合)", "r": "step", "key": "round" }
// 之后：
{ "l": "...", "loopTo": "round" }
// 或分支小循环：
{ "l": "允许", "res": "下一项再弹 ↺ (W·同回合内)", "r": "option", "loop": true }
```

**⑤ 标优先级与归属测试**（治理字段，图生成器不消费）：

```jsonc
{ "id": "f-xxx", "label": "...", "p": "P0", "spec": ["tests/e2e/x.spec.ts"], "chain": [...] }
```

**⑥ 重命名模块或功能**：改 `label`；`id` 除非身份本身变了否则保持不变——治理
报表与 spec 归属都按 id 关联。
