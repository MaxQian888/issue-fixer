# 先验证，再动手

输入是「一个论断」，输出是「判定 + 证据 + 动作」。两种失败都要防：没验证就改（把对的
改错）、没证据就下结论。

## 1. 拆命题

把论断拆成可证伪命题："文件 F 第 L 行在条件 C 下产生错误行为 B"。拆不出来 → 问用户
担心的具体行为是什么。

- **完成判据**：每条命题能被一次代码阅读或一次运行证伪。

## 2. 取证

- 读**当前**代码：先核对论断针对的版本是否已变（"最新的代码是不是已经修了"要先查证）。
- 沿调用链确认路径可达：谁调、入参可能值、前置条件。
- **完成判据**：每条命题凑齐"触发条件 + 代码路径 + 预期行为"三元组，或明确指出缺哪一环。

## 3. 判定 → 动作

| 判定 | 动作 |
|---|---|
| 证实是问题 | 给证据后直接最小修复（"是问题就修复"句式已含授权） |
| 证否 / 已修复 | 给反证（哪行已覆盖、什么条件下不触发），工作区不动 |
| 证据不足 | 说清缺什么 + 可做的验证手段（复现/加日志/跑测试），问用户要不要继续 |

报告格式与实例见 [references/verdict-format.md](references/verdict-format.md)。

- **完成判据**：每条命题都有判定；修复的改动能指认到被证实的命题。

## 4. 性能类论断：实测

- 优化声明用前后对比回答：接口计时、渲染次数、bundle 体积等可复现指标。
- 采样走真实链路（已登录会话、真实接口），mock 数据不算数。
- **完成判据**：报告含指标、优化前、优化后、测量方法、样本量五要素。
