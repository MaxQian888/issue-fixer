# UI 原型

在**一条路由**上生成**几个截然不同的 UI 变体**，用悬浮底栏切换。用户在浏览器里翻变体，挑一个（或各取所长），其余扔掉。

问题是逻辑/状态而非长相——走错分支，用 [LOGIC.md](LOGIC.md)。

## 什么时候用这个形态

- "这个页面应该长什么样？"
- "定稿前我想看这个 dashboard 的几个方案。"
- "给设置页换个布局试试。"
- 任何用户原本要在脑里纠结三个模糊稿一整天的场景。

## 两个子形态——强烈优先 A

UI 原型**贴着应用其余部分**时才容易评判——真实 header、真实侧栏、真实数据、真实密度。孤立的一次性路由是真空：每个变体单看都挺好。只要有可信的现存页面能承载变体，默认子形态 A。原型确实没有邻近归宿时才用子形态 B。

### 子形态 A——在现有页面上调整（首选）

路由已存在。变体渲染在**同一条路由**上，由 `?variant=` URL search 参数门控。现有数据获取、params、认证全保留——只换渲染。这是默认；没有具体理由别选别的。

如果原型对象还没有页面但*本来就该长在某页面里*（dashboard 新板块、设置页新卡片、现有流程新步骤）——那仍是子形态 A，把变体挂进宿主页面。

### 子形态 B——新页面（兜底）

仅当被原型对象真的没有现有页面可装——如全新顶层界面、或无法合理嵌入的流程——才用。

按项目已有路由约定建**一次性路由**——别发明新顶层结构。命名要一眼看出是原型（路径或文件名里带 `prototype`）。同样的 `?variant=` 模式。

承诺子形态 B 前先 sanity-check：真的没有现成页面可以嵌吗？空路由会掩盖 populated 页面会暴露的设计问题。

两个子形态的悬浮底栏完全一样。

## 流程

### 1. 写下问题，定 N

默认 **3 个变体**。超过 5 个就不再"截然不同"而变成噪音——封在 5。

在原型位置或文件顶部注释里写一行计划：

> "设置页三个变体，现有 `/settings` 路由上，用 `?variant=` 切换。"

用户在与不在都适用。

### 2. 生成截然不同的变体

逐个起草。每个变体守住：

- 页面的目的和它能拿到的数据。
- 项目的组件库/样式体系（TailwindCSS、shadcn、MUI、纯 CSS，whatever）。
- 清晰的导出组件名，如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——不同布局、不同信息层级、不同主操作，不只是换色。三个微调过的卡片网格不是 UI 原型，是墙纸。两个草稿太像，就用"不许用卡片网格"这种明确约束重做一个。

### 3. 接线

在路由上建一个切换组件：

```tsx
// 伪代码——按项目框架适配
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页）：切换器以上保留全部现有数据获取；每个变体只换渲染子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂同一个切换器。

### 4. 做悬浮切换条

屏幕底部居中的小固定条，三个部件：

- **左箭头**——切到上一个变体（循环）。
- **变体标签**——显示当前变体 key，变体导出了名字就带上，如 `B — Sidebar layout`。
- **右箭头**——切到下一个（循环）。

行为：

- 点箭头更新 URL search 参数（用框架 router——Next 用 `router.replace`，React Router 用 `navigate`），变体可分享、刷新不丢。
- 键盘：`←` `→` 也切换。`<input>`、`<textarea>`、`[contenteditable]` 聚焦时不要拦截方向键。
- 视觉上与页面区分（高对比 pill、轻阴影），让人一眼知道它不是被评估设计的一部分。
- 生产构建隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价检查门控，原型误合并也不能把条子发给用户。

切换条做成单个共享组件，两个子形态复用。放项目共享 UI 所在处。

### 5. 交出去

给出 URL（和 `?variant=` 键）。用户有空会自己翻。最有意思的反馈通常是**"我要 B 的 header 配 C 的侧栏"**——那才是他们真正要的设计。

### 6. 记下答案并清理

变体定胜负后，写下哪个赢了为什么（commit message、ADR、issue；或 AFK 且用户未回时原型旁的 `NOTES.md`）。然后：

- **子形态 A**——删掉落选变体和切换条；把胜者折进现有页面。
- **子形态 B**——把胜出变体提升为正式路由，删掉一次性路由和切换条。

别留变体组件或切换条在仓库里，烂得快还迷惑下一位读者。

## 反模式

- **只换颜色或文案的变体。** 那是微调不是原型。真变体在结构上互不同意。
- **变体间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就失去意义。每个变体都要有推翻布局的自由。
- **把变体接真实 mutation。** 只读原型就行。变体需要写就指向 stub——问题是"该长什么样"，不是"后端通不通"。
- **原型直接上生产。** 变体代码是在原型约束下写的（无测试、最小错误处理）。折进去时按生产标准重写。
