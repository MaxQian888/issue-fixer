# Bugfix 复核

启动一个**独立上下文**的子代理执行复核。只给它三样东西：

- 用户的问题描述：触发方式、症状、期望行为（有就带上）；
- 待审改动：用户指定的 diff 范围，默认当前工作区改动；
- 下面的评审规则。

**不要**把此前的诊断过程、实现理由或期望结论放进子代理上下文——它会污染裁决。
返回子代理输出的精简 Markdown 评审。

## 评审规则

1. 识别所报告的触发方式、症状与期望行为。
2. 识别被审代码实际改变了什么行为。
3. 追踪因果链：报告的触发 → 改动代码被触达 → 相关状态或输出变化 →
   报告的症状或期望行为被影响。
4. 裁决基于链条上那个决定性的「已覆盖 / 仍断裂 / 证据不足」环节。

裁决只用三选一：

- `从代码看已修复`：证据支持因果链的每个必要环节。
- `从代码看未修复`：证据确立至少一个必要环节仍然断裂。
- `暂无法确认是否修复`：问题描述、diff 或邻近代码不足以支撑任一结论。

多个显式问题分别判定，整体裁决取最弱的相关结果。聚焦报告的问题路径和同一
行为契约内引入的回归；忽略无关的风格、架构和既有问题。每个关键判断给出具体
代码位置和一句因果解释。宁缺证据，不靠推测。

## 输出

返回精简 Markdown：

```md
## 结论
<三选一裁决 + 决定性理由>

## 关键依据
- <代码位置 + 因果解释>

## 风险与边界
- <只写实质性的不确定项或验证缺口；无则省略本节>
```

## 与本插件流水线的关系

`bugfix-review` 是独立工具，也是 `issue-orchestrator` 第 13 步 `review` 的执行者：M/L 档
在 Gate ② 之前必须用它复核（S 档用自查清单，也可以用它）。在流水线里调用时，问题描述取
指纹里的用户原文与复现记录，待审改动取 `$BASE...HEAD` 加工作区，仍然不带诊断过程。裁决
"从代码看未修复"会把流水线送回改码步骤。单独使用时绝不触发 issue-fixer 的交付门禁——它
只产出裁决，不改代码。
