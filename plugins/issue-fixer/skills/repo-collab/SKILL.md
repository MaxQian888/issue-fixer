# 仓库协作契约

本契约治理目标仓库里的一切动作。流水线（issue-orchestrator）的三个门禁是它的显式授权；
门禁之外仍逐指令批准。

## 授权边界

- **先确认**：方案有分叉、语义不明、改动超出任务范围、删用户已有代码、冲突需要二选一。
- **直接做**：冲突中双方 `都保留` 的项、已批方案的执行细节、明确的机械修复。
- **推送要显式授权**：出现"提交并且推送""直接推送"才 push；"提交"只到 commit。
  rebase 后推送用 `git push --force-with-lease`。
- **范围纪律**：每个改动文件能回答"哪条验收点需要它"。顺带重构、格式化无关代码超出授权。

## 证据标准

- 性能结论给前后实测：指标、优化前、优化后、方法、样本量。
- 论断真伪先给代码证据再给结论；没跑过的检查不出现在汇报里。
- 采样走真实链路：已登录浏览器会话、真实接口、真实数据。

## 验证力度 = 改动面

| 改动面 | 档位 |
|---|---|
| 纯样式/文案 | lint + 目视/截图 |
| 逻辑/缺陷 | 最窄 owning layer 测试 + 受影响包构建 |
| 用户可见/协议变更 | `e2e-check` 判定是否补 E2E |
| 性能 | 前后实测数据 |

小任务求利落：快速确认、直接修、短汇报，不套重型流程（spec/plan 模板之类）。
验证命令取 `verify.lint`/`verify.typecheck`/`verify.test` 配置，未配置时从仓库
工具链推断（见 worktree-flow 的 verify-matrix）。

## 前端约定

- 样式跟随仓库已声明的体系（Tailwind、CSS Modules、scss……读最近的 AGENTS.md/仓库配置，
  不要自作主张引入第二种）。
- 设计稿对齐：字体、颜色、间距、选中态、动画逐项比对；严格遵守用户指定的排除区域。
- 组件与能力先复用仓内已有实现，再考虑新写。

## 工具定位

- **仓库自带 CLI/子依赖优先**：排查期间用现成版本，不安装不升级；仓库锁定的工具链优先于
  PATH 上的同名全局命令。
- **报告/通知**：走 `report`/`notify` 适配器配置（markdown 落盘、飞书文档、群消息……），
  不直调平台 API。
- **浏览器取证**：接管用户已登录标签页操作，保持会话与数据真实；绝不导出 cookie/token。

## 沟通

用用户语言汇报；链接类输入（MR / 文档 / 设计稿 / 任务）先解析再动手；被纠偏时按新指令
直接执行。
