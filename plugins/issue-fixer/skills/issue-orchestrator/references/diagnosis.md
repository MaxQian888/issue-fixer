# 复现、定位与根因

`reproduce`、`locate`、`red`、`fix` 四步共用的诊断方法。UI 问题的截图→组件映射由
`ui-issue-localize` 负责；本文件管所有分类共有的部分，以及报错/后端/数据/性能/配置类
问题的日志驱动定位。

## 1. 复现（reproduce）——在基线上看到症状

目标：一个在当前 `origin/<base>` 上可观察、可重复的症状，写成 `repro` 记录：

```yaml
repro:
  status: reproduced | not-reproduced | not-attempted
  method: string          # 命令 / 路由 + 操作 / 请求 / 日志查询
  environment: {}         # 只写观察到或被提供的维度；推断值标注 inferred
  observed: string        # 实际看到的，逐字引用报错首行或测得的属性值
  expected: string
  attempts: [{ environment: {}, result: string }]
```

- 复现在 Gate ① 之前做，且不改产品代码：查日志、读已有数据、对远程后端发请求。需要运行
  `origin/<base>` 的代码（跑已有测试、起 local-dev、确认是否已修）时用探针 worktree
  `<runDir>/probe`（detached，见 SKILL.md 第 3 步）；新写的回归测试属于 `red` 步骤，在修复
  worktree 里写。
- 复现不了时，用 **IS / IS NOT** 表收窄差异——对每个维度写"出问题的情况是 … / 没出问题
  的情况是 …"：版本/提交、浏览器/引擎、OS/设备、视口、语言/时区、账号角色/权限、
  feature flag、数据形态（空/超长/特殊字符/大量）、网络（慢/断/重试）、时间（首次/并发/
  缓存命中）。两列差异最大的维度就是下一次尝试的方向，也是向提出人要的那一个问题。
- 间歇性问题：重复同一复现 N 次（默认 20）记录失败率；修复要用同样的 N 证明失败率下降，
  而不是一次通过。
- `not-attempted` 只在复现需要用户独有的账号/数据/环境时成立，写明卡在哪，并在 Gate ①
  前问出来。

## 2. 分层定位（locate）——文件 → 符号 → 行

先窄后深，每一层记下用了什么搜索词、排除了什么，让结论可复现：

1. **区域**：模块/路由/服务 → 包与目录（路由表、仓库 AGENTS.md、目录约定、调用链）。
2. **文件**：在区域内搜症状的字面量——报错消息、日志 key、接口路径、可见文案、埋点名。
   报错消息的出处通常就是抛出点，但抛出点不一定是缺陷点。
3. **符号**：沿调用链找"错误状态第一次产生"的函数，而不是"错误第一次被发现"的函数。
4. **行**：缺陷所在行 + 必须一起改的耦合值。

**日志驱动**（有 runId/logid/stack trace/HTTP 状态时）：

- runId/logid → 用仓库自己的日志/排障工具取完整日志；拿不到就摆出确切的取数命令与
  所需权限并问，不凭 ID 样式猜内容。
- 以请求 ID/时间戳把前后端日志串起来，找**第一条**异常，不是最后一条。
- 栈帧从上往下找第一个属于本仓的帧；vendor/框架帧只说明调用路径。
- 压缩/打包后的栈先用 source map 还原，还原不了就在报告里写明。

**两个独立锚点**才能断言定位（`ui-issue-localize` 的置信度规则同样适用于非 UI）：
例如 报错消息出处 + 调用链可达、失败测试 + 断点位置、日志字段 + 写入该字段的代码。

## 3. 根因——因果链

Gate ① 必须带一条**因果链**：

```text
触发（用户操作/输入/时序） → 代码路径（file:line …） → 错误状态（哪个值/哪个分支错了）
→ 症状（用户看到的）
```

M/L 档再加 **为什么现在**：

- 提出人说"以前是好的"、给了版本或时间点、或症状出在最近改过的代码上 → 找引入提交：
  `git log -S '<字面量>'`、`git log -L :<函数>:<文件>`、`git blame -w -C` 缺陷行。
- 复现能写成确定性命令且单次很快时，可在探针 worktree `<runDir>/probe`（不是修复
  worktree）里做有界 `git bisect run <命令>`，步数上限约 12；超限就停，报告已收窄的范围；
  结束后 `git -C <runDir>/probe bisect reset`。
- 找到的引入提交写进 `regressionOf`。若该提交可独立回退且回退就是最小修复，在 Gate ①
  把"回退 vs 前向修复"作为两个选项呈现。

**症状修复自检**——方案提交 Gate ① 前逐条回答：

- 只改这一处，其他能产生同一错误状态的路径是否仍然坏？
- 改动是否把上游的错误藏起来了（吞异常、加兜底默认值、加空值判断、放宽校验、加重试/
  延时）？
- 修的是错误状态产生的地方，还是被发现的地方？

任一答案指向"只压住了症状"，就把 `fixKind` 定为 `mitigation` 或 `workaround` 并在
Gate ① 说明未消除的根因；不能把止血说成根因修复。

## 4. 影响面与同类缺陷

- **影响面**：改动符号的全部调用方（grep / LSP 引用 / 导出面）；共享组件列出使用它的
  页面。M/L 档写进 Gate ① 卡片。
- **同类缺陷**：用缺陷的代码形态（同样的错误用法、同样的魔法值、同样漏掉的分支）在仓库
  里搜一遍。命中项写进 `followUps`；与本问题**同一根因、且在已批方案范围内**的才顺手修，
  否则单独提议，不扩大本次 diff。

## 5. 红灯 → 绿灯（red / fix）

- **红灯**：worktree 建好、编辑之前，在 `$BASE` 上让问题以可观察的方式失败——
  - 逻辑/报错/数据：最窄归属层的回归测试（仓库已有的 runner 与目录约定），失败原因必须
    就是所报症状（断言信息对得上），不是编译错误或无关失败。
  - UI 样式/文案：`before` 截图 + 实测的变化属性（高度、颜色、文本）。
  - 无测试 harness：脚本化复现（`<runDir>/repro.sh` 或等价命令），不在仓外造 harness。
  - 性能：基线实测（指标、方法、样本量）。
- **绿灯**：修复后同一检查通过；再跑受影响的既有测试集确认没有新的失败
  （"原来过的仍然过"）。
- 回归测试进交付 diff（它是修复的一部分）；脚本化复现与性能采样脚本留在 `<runDir>`，
  不进 diff。

## 6. 假设日志

每次"我认为原因是 X"都记一条到 `<runDir>/hypotheses.md`，失败的也记：

```markdown
## H<n> · <一句话假设>
- 预测：若假设成立，<某检查> 会 <某结果>
- 实验：<改动或命令>
- 结果：<实际输出>
- 结论：成立 / 不成立 / 部分成立（→ 下一步）
```

熔断预算按失败假设计数（见 [sizing.md](sizing.md)）。熔断回 Gate ① 时把这份日志作为
证据呈现，让用户看到排除了什么。
