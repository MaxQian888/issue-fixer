# 逻辑原型

一个极小的交互式终端应用，让用户亲手驱动一个状态模型。当问题关乎**业务逻辑、状态流转或数据形状**时使用——那种纸面上看着合理、但只有推进真实 case 才觉得不对的东西。

## 什么时候用这个形态

- "我不确定这个状态机能不能处理先 X 后 Y 的边界 case。"
- "这个数据模型真的能表达……这种情况吗？"
- "想在写之前先摸清这个 API 应该长什么样。"
- 一切用户想**按按钮看状态变化**的场景。

问题是"应该长什么样"就走错分支了，用 [UI.md](UI.md)。

## 流程

### 1. 写下问题

写代码前，先写下你在打样的状态模型和要回答的问题。一段话，放原型的 README 或文件顶部注释。答错问题的逻辑原型是纯浪费——把问题写明白，之后才能核对，不管用户现在在看还是 AFK 后回来。

### 2. 选语言

用宿主项目在用的语言。项目没有明显 runtime（如纯文档仓库）就问。

工具链遵守项目现有约定——别为原型引入新包管理器或 runtime。

### 3. 把逻辑隔离成可移植模块

把真正在回答问题的逻辑放在一个小而纯的接口后面，之后能拎出来直接放进真实代码库。外面的 TUI 是一次性的；逻辑模块不该是。

正确形态取决于问题：

- **纯 reducer** —— `(state, action) => state`。动作是离散事件、状态是单值时合适。
- **状态机** —— 显式状态与转移。"现在哪些动作合法"本身是问题时合适。
- **一组操作普通数据类型的纯函数**。没有隐式当前状态、只有变换时合适。
- **有清晰方法面的 class 或模块**——逻辑确实持有持续内部状态时。

选最贴合所问问题的形态，而不是最容易接 TUI 的。保持纯：无 I/O、无终端代码、不用 `console.log` 做控制流。TUI import 它、调用它；反向什么都没有。

这让原型活过自身寿命。问题答完，验证过的 reducer/状态机/函数集可以拎进真实模块——TUI 壳删掉。

### 4. 做最小的能暴露状态的 TUI

做成**轻量 TUI**：每个 tick 清屏（`console.clear()` / `print("\033[2J\033[H")` / 等价物）并重绘整帧。用户始终看到一个稳定视图，而不是不断增长的滚动回滚。

每帧两部分，按此顺序：

1. **当前状态**，pretty-print 且易 diff（每字段一行或格式化 JSON）。字段名/小节标题用**粗体**，次要上下文（时间戳、ID、派生值）用**暗色**。原生 ANSI 转义就够——`\x1b[1m` 粗体、`\x1b[2m` 暗、`\x1b[0m` 重置。项目里没有就别引样式库。
2. **快捷键**，列在底部：`[a] add user  [d] delete user  [t] tick clock  [q] quit`。键加粗、说明变暗，或反过来——读着清楚就行。

行为：

1. **初始化状态**——单个内存对象/结构体。启动即渲染第一帧。
2. **一次读一个按键（或一行）**，分发到会改状态的 handler。
3. **每次动作后重绘整帧**——不追加，替换。
4. **循环直到退出。**

整帧应该一屏放得下。

### 5. 一条命令可跑

在项目现有 task runner 里加 script（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户跑 `pnpm run <prototype-name>` 或等价命令——永远不需要记路径。

宿主项目没有 task runner，就把命令写在原型 README 顶部。

### 6. 交出去

把运行命令给用户。他们会自己开；有意思的瞬间是"等等，这不应该能发生"或"咦，我以为 X 会不一样"——那些是**想法**里的 bug，这正是原型意义。想加动作就加。原型会演化。

### 7. 记下答案

原型完成使命后，问题的答案是唯一值得留的东西。用户在就问学到了什么；不在就在原型旁留 `NOTES.md`，删原型前把答案填上（或由旁听完会话的你填）。

## 反模式

- **别加测试。** 需要测试的原型不再是原型。
- **别接真实数据库。** 用内存存储，除非问题专门针对持久化。
- **别泛化。** 没有"万一以后要支持 X"。原型只回答一个问题。
- **别把逻辑和 TUI 搅在一起。** reducer/状态机引用 `console.log`、prompt 或终端转义码，就不可移植了。TUI 保持为纯模块上的薄壳。
- **别把 TUI 壳带进生产。** 壳是为终端手操优化的；后面的逻辑模块才值得留。
