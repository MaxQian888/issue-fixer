# 用户路径脑图

通过一条源码可控的管线维护目标仓库的用户路径/CUJ 模型：

```text
tree.json ── 仓库生成器 ──> diagram ── 可选白板通道 ──> 共享白板
    └── p/spec ──> 仓库 CUJ 校验器 ──> 治理检查与报表
```

`tree.json` 是唯一手工编辑的路径源。派生图、白板、报告都是**派生产物**。绝不从生成
产物反向修复或逆向工程 `tree.json`。

本 skill 只提供**流程纪律**——`tree.json`、校验器、生成器、白板推送全部归目标仓库
所有，由 `fixer.config.json` 的 `mindmap` 配置定位：

```jsonc
{
  "mindmap": {
    "dir": "docs/user-path-mindmap",   // 相对 repoDir；默认就是这个
    "lintCommand": "node docs/user-path-mindmap/lint-tree.mjs",
    "buildCommand": "node docs/user-path-mindmap/gen.mjs",
    "pushCommand": ""                  // 可选；同步共享白板的仓库自有命令
  }
}
```

## 先做 preflight

1. 用 `git rev-parse --show-toplevel` 解析目标仓库；不要假设固定的 checkout 或分支。
2. 编辑前读适用的仓库 `AGENTS.md`，再读脑图目录自己的 README 与校验器说明。
3. 查 `git status --short`，保留无关或未跟踪的用户工作。
4. 当前 checkout 必须存在这些源文件：
   - `<mindmap.dir>/tree.json`
   - 仓库自有的校验器与生成器入口（`lintCommand`/`buildCommand` 指向的脚本）
5. 文件缺失就停下。报告当前分支不含脑图源文件，询问哪个分支/worktree 是权威。
   未经显式授权，不从历史拷贝、不切分支、不重建。

改动拓扑、角色、回环、轮次语义、优先级或 spec 映射前，先读
[`references/tree-schema.md`](references/tree-schema.md)。

## 归类本次改动

| 改动 | 编辑 `tree.json` | 重建本地产物 | 推送白板 | 更新文档 |
|---|---:|---:|---:|---:|
| 加/删/改功能或路径 | 是 | 是 | 按需（门禁） | 仅当路径事实变化 |
| 仅改优先级/spec 归属 | 是 | 否 | 否 | 按需更新台账 |
| 纯重生成/同步 | 否 | 是 | 按需（门禁） | 否 |
| 配套文档编辑 | 仅当路径事实变化 | 按需 | 按需 | 是 |

改动保持外科手术式。更新一条路径的请求不授权做无关的分类清理、E2E 实现、
文档重写、提交或分支变更。

## 编辑源文件

1. 定位归属的 `branches[]` 模块与 `functions[]` 节点。
2. 改路径语义前，对照当前代码核实用户可见行为。数值区间、超时、状态流转、
   轮次边界都要在实现处核实；不要凭脑图上的历史值做假设。
3. 编辑最小 JSON 区域。除非身份本身变了，否则保留稳定 ID。不要重排整个文件。
4. 单线 sequential 路径用 `chain`，分叉/合流行为用 `flow`。锚点和 `loopTo`
   保持在同一个 function 内。
5. `p` 表示治理优先级，`spec` 表示归属测试。优先级取值与 spec 根目录以当前
   仓库校验器定义为准——不要假设一套固定值。
6. 若请求改变了产品行为但没有归属测试，报告覆盖缺口。仅当用户同时要求实现
   或补测时才新增/修改测试。

不要把易变的项目计数写进文字。模块/function/优先级/spec 计数每次跑都从仓库
校验器或生成器推导。

## 用仓库自有规则校验

优先用仓库入口（`mindmap.lintCommand`）；它是契约且可能演进：

```bash
<mindmap.lintCommand>          # 例：node docs/user-path-mindmap/lint-tree.mjs
```

不要用自造的 JSON 解析或重复 linter 替代仓库校验。按通行约定，校验应覆盖：

- 合法的树结构和全局唯一的 function ID；
- 合法的优先级取值与（若仓库有）P0 预算；
- `spec` 类型合法性及在仓库支持的测试根下的存在性；
- 每个最高优先级节点都有归属测试；
- 提供测试结果文件时可选的执行状态检查。

拓扑变了的话，用仓库生成器重建派生产物（`mindmap.buildCommand`）。汇报生成器的
module/function 计数与校验器摘要——与预期 delta 对比，不要与写死的历史总数对比。

## 同步共享白板（有 pushCommand 时，门禁顺序）

1. 跑仓库校验和本地 build。
2. 向用户展示源码 diff、预期拓扑 delta、生成器计数、目标白板身份。
3. 取得对整板覆盖写这一破坏性操作的**显式确认**。
4. 白板身份从仓库文档/配置发现，不要相信未经核对的拷贝 token。
5. 运行 `mindmap.pushCommand`。
6. 要求成功的更新响应和节点/连线创建摘要。

白板必须以整板一次性写入；单独追加连线会产生非法链接。用户请求改源文件
**不等于**批准覆盖共享白板。

## 更新配套文档

仅当事实变化时更新仓库台账或设计文档。带日期的快照视为历史证据；追加带日期的
更新或通过归属工作流重新生成，不要静默改写历史。编辑在线文档走文档工具的原子
块操作，避免整文档覆盖——整文档覆盖是破坏性操作，可能移除评论和嵌入内容，需
单独的显式确认。

## 完成门禁

宣称完成前，为每个执行过的动作给出证据：

- 仓库校验器通过；
- 拓扑变化时生成器通过；
- 源码 diff 与请求的路径 delta 一致；
- 没有生成产物被手改或被意外 stage；
- 白板更新返回成功（若已批准并执行）；
- 编辑过的在线文档小节已回读核对；
- `git status --short` 只显示预期的本地改动。

分开汇报：源码改动、校验结果、本地生成产物、远程写入、以及残余的治理或覆盖缺口。
